# Spec: Verde Marea — система бронирования столов

## 1. Назначение

Verde Marea — небольшой ресторан средиземноморской кухни на набережной: зал и веранда, восемь столов от двух до восьми мест, кухня работает со вторника по воскресенье, понедельник — выходной. Гости сейчас бронируют по телефону, хостес ведёт тетрадь, и столы теряются.

Система бронирования заменяет тетрадь: гость сам выбирает дату, время и число гостей и видит только реальные свободные варианты; администратор ведёт поток бронирований и окна записи; владелец (super_admin) управляет ролями сотрудников. Это учебный MVP с локальным запуском (финальный проект модуля 4 курса «Вайбкодинг»).

## 2. Пользователи и сценарии

**Роли** (гость без входа — это отсутствие сессии, отдельной роли в базе нет):

| Роль | Кто | Что важно |
|------|-----|-----------|
| `user` | гость ресторана | быстро выбрать дату, время, число гостей; видеть свои бронирования и уведомления; отменить, пока можно |
| `admin` | хостес / администратор зала | видеть поток бронирований, подтверждать, отменять, завершать, отмечать неявку; закрывать окна; видеть, какой стол назначен |
| `super_admin` | владелец | всё, что admin, плюс повышение `user` → `admin` и понижение обратно |

**Пользовательский сценарий:**

1. Гость открывает сайт, регистрируется (имя, почта, пароль) или входит. Открывается сессия.
2. На странице «Забронировать» выбирает дату (только ближайшие 14 дней, без понедельников) и число гостей.
3. Видит только допустимые окна этого дня. Если окон нет — сообщение «На эту дату нет свободных окон» и подсказка выбрать другую дату или меньше гостей.
4. Нажимает окно → создаётся бронирование `pending`, система назначает самый маленький подходящий свободный стол.
5. В «Моих бронированиях» видит бронирование, стол, статус и внутренние уведомления.
6. Может отменить бронирование не позднее чем за 3 часа до начала; позже кнопки нет, а сервер и база отклоняют попытку.

**Административный сценарий:**

1. admin открывает «Администрирование» → «Бронирования», фильтрует по статусу и дате.
2. Видит гостя, число гостей, стол, статус и доступные переходы; подтверждает, отменяет, завершает, отмечает `no_show`.
3. В «Окнах записи» закрывает отдельное окно или весь день (например, банкет) и открывает обратно.
4. В «Пользователях» видит список; кнопки смены роли видит только super_admin.
5. В «Истории» видит, кто и когда создал, подтвердил, отменил, завершил бронирование, отметил неявку, сменил роль, закрыл или открыл окно.

**Служебный сценарий (super_admin):** повышает пользователя до `admin` или понижает до `user`; изменение попадает в историю. Роль `super_admin` через интерфейс не выдаётся и не снимается.

**Крайние случаи:** гость без сессии на защищённой странице → `/login`; `user` в `/admin` → экран «Нет доступа»; окно заняли между показом и нажатием → понятная ошибка и обновлённый список.

## 3. Сущности и поля

Типы — PostgreSQL/Prisma. Время хранится в UTC (`timestamptz`), правила считаются во времени ресторана `Europe/Moscow` (UTC+3).

### User

| Поле | Тип | Обяз. | Описание |
|------|-----|-------|----------|
| `id` | text (cuid) | да | |
| `name` | text | да | 2–60 символов |
| `email` | text, unique | да | в нижнем регистре |
| `passwordHash` | text | да | `bcryptjs.hash(password, 12)`; никогда не уходит в UI и ответы |
| `role` | enum `Role` | да | `user` по умолчанию |
| `createdAt`, `updatedAt` | timestamptz | да | |

### Session

Серверная сессия auth-lite: `tokenHash` (SHA-256 токена из httpOnly-cookie, unique), `userId`, `expiresAt` (7 дней).

### Table

| Поле | Тип | Обяз. | Описание |
|------|-----|-------|----------|
| `id` | text | да | |
| `code` | text, unique | да | `T1`…`T8` |
| `zone` | text | да | «Зал» / «Веранда» |
| `capacity` | int | да | CHECK 1–12 |
| `isActive` | bool | да | неактивный стол не назначается |
| `shape` | text | да | `round` / `rect` — форма на плане зала |
| `planX`, `planY` | int | да | центр стола на плане, координаты в системе 1000 × 640 |
| `planW`, `planH` | int | да | размер стола на плане (для `round` — `planW` = диаметр) |

План зала (версия 2, пет-проект): зал слева, веранда справа у «моря»; восемь столов расставлены seed-данными, пересечений нет. Кроме столов на плане есть неинтерактивные ориентиры: вход, бар, открытая кухня, окна к морю.

### SlotClosure — механизм окон записи

Окна **не хранятся списком**: они вычисляются по правилам раздела 5. `SlotClosure` — явное исключение из правил, которое заводит администратор.

| Поле | Тип | Обяз. | Описание |
|------|-----|-------|----------|
| `id` | text | да | |
| `date` | date | да | день ресторана |
| `startTime` | text `HH:MM` | нет | `null` — закрыт весь день; иначе одно окно |
| `reason` | text | да | например «Банкет» |
| `createdById` | text → User | да | |
| `createdAt` | timestamptz | да | |

Уникальность: одно закрытие на (`date`, `startTime`) и одно на весь день.

### Booking

| Поле | Тип | Обяз. | Описание |
|------|-----|-------|----------|
| `id` | text | да | |
| `userId` | text → User | да | владелец |
| `tableId` | text → Table | да | назначенный стол |
| `startsAt` | timestamptz | да | начало окна |
| `endsAt` | timestamptz | да | CHECK `endsAt = startsAt + 90 минут` |
| `guests` | int | да | CHECK 1–8 и `guests ≤ capacity` стола (триггер) |
| `status` | enum `BookingStatus` | да | `pending` по умолчанию |
| `createdAt`, `updatedAt` | timestamptz | да | |

Ограничения базы:

- `Booking_table_no_overlap` — EXCLUDE (`tableId` =, `tstzrange(startsAt, endsAt)` &&) для `pending`/`confirmed`: один стол не назначается двум активным бронированиям на пересекающееся окно.
- `Booking_user_no_overlap` — EXCLUDE (`userId` =, `tstzrange` &&) для активных: у пользователя нет двух активных бронирований на одно время.

```json
{ "id": "ck…", "userId": "ck…", "tableId": "ck…", "startsAt": "2026-10-20T15:00:00Z", "endsAt": "2026-10-20T16:30:00Z", "guests": 4, "status": "pending" }
```

### Notification

Внутреннее уведомление владельцу бронирования: `userId`, `bookingId`, `type` (`booking_created`, `booking_confirmed`, `booking_cancelled`, `booking_completed`, `booking_no_show`), `message`, `readAt`, `createdAt`. Составной FK (`bookingId`, `userId`) → Booking(`id`, `userId`): уведомление нельзя привязать к чужому пользователю.

### AuditLog

| Поле | Тип | Описание |
|------|-----|----------|
| `actorId` | text → User | кто сделал |
| `action` | enum `AuditAction` | `booking_created`, `booking_confirmed`, `booking_cancelled`, `booking_completed`, `booking_no_show`, `role_changed`, `slot_closed`, `slot_opened` |
| `bookingId` | text, null | для действий с бронированием |
| `targetUserId` | text, null | для смены роли |
| `details` | jsonb | `{from, to}` для статуса/роли, дата и время для окна |
| `createdAt` | timestamptz | когда |

Записи AuditLog и Notification создают функции PostgreSQL в той же транзакции, что и изменение, — действие без записи в истории невозможно.

## 4. Статусы и переходы

| Значение | Подпись | Смысл |
|----------|---------|-------|
| `pending` | Ожидает подтверждения | создано гостем |
| `confirmed` | Подтверждено | администратор подтвердил |
| `cancelled` | Отменено | гостем или администратором |
| `completed` | Состоялось | гость пришёл |
| `no_show` | Неявка | гость не пришёл |

| Из → в | Кто | Условие |
|--------|-----|---------|
| `pending` → `confirmed` | admin, super_admin | до начала окна |
| `pending`/`confirmed` → `cancelled` | владелец | не позднее чем за 3 часа до начала |
| `pending` → `cancelled` | admin, super_admin | в любое время (до и после начала окна) |
| `confirmed` → `cancelled` | admin, super_admin | до начала окна |
| `pending`/`confirmed` → `completed` | admin, super_admin | после начала окна (гость пришёл) |
| `pending`/`confirmed` → `no_show` | admin, super_admin | после начала окна (гость не пришёл) |

- Неподтверждённое бронирование не «зависает» после начала окна: администратор закрывает его как `completed`, `no_show` или `cancelled` (изменение 2026-10-15).
- `cancelled`, `completed`, `no_show` — терминальные: правила возврата в активный статус нет, триггер базы отклоняет такую смену.
- Новые статусы добавляются только вместе с обновлением этой спецификации.

## 5. Правила окон и бронирования

Одинаковые в интерфейсе (`lib/booking/rules.ts`), на сервере (Server Actions через те же функции) и в базе (`vm_*` в миграции `booking_rules`):

- **Горизонт:** сегодня и ещё 13 дней (14 дней ресторана).
- **Дни:** вторник–воскресенье; понедельник закрыт.
- **Окна:** начало 12:00, 13:30, 15:00, 16:30, 18:00, 19:30; длительность 90 минут (последнее заканчивается в 21:00).
- **Без прошлого:** окно, которое уже началось, не показывается и не бронируется.
- **Без закрытых:** окно или день из `SlotClosure` не показывается и не бронируется. Закрытие не отменяет уже созданные бронирования.
- **Без занятых:** окно показывается, только если есть активный стол с `capacity ≥ guests`, свободный в это окно, и у пользователя нет активного бронирования на это время.
- **Подбор стола:** самый маленький подходящий свободный стол (по `capacity`, затем по `code`) — по умолчанию, кнопка «Подобрать автоматически».
- **Выбор стола на плане (версия 2):** гость может сам выбрать стол на плане зала для выбранной даты и окна. Можно выбрать только активный стол, свободный в это окно, с `guests ≤ capacity ≤ guests + 2` (двое не занимают стол на восемь). Статусы стола на плане: `free` (можно выбрать), `busy` (занят в это окно), `unsuitable` (не подходит по вместимости), `closed` (окно закрыто). Та же проверка — в функции PostgreSQL: `vm_create_booking` получает необязательный `p_table_id`; если стол передан и не проходит правило — ошибка `VM_TABLE_UNAVAILABLE`, гонка двух гостей за один стол по-прежнему ловится `Booking_table_no_overlap`.
- **Свободные столы по окнам:** в полосе окон дня у каждого окна показано число свободных подходящих столов (`vm_table_availability`).
- **Гости:** 1–8 (максимальная вместимость стола).
- **Дедлайн отмены гостем:** `now ≤ startsAt − 3 часа`.

## 6. Матрица ролей

| Действие | гость (без входа) | user | admin | super_admin |
|----------|:-:|:-:|:-:|:-:|
| Регистрация, вход | ✓ | — | — | — |
| Смотреть доступные окна | — | ✓ | ✓ | ✓ |
| Создать бронирование на себя | — | ✓ | ✓ | ✓ |
| Свои бронирования и уведомления | — | ✓ | ✓ | ✓ |
| Отменить своё (≥ 3 ч до начала) | — | ✓ | ✓ | ✓ |
| Административный контур `/admin` | — | — | ✓ | ✓ |
| Подтвердить / отменить / завершить / no_show | — | — | ✓ | ✓ |
| Закрыть и открыть окно или день | — | — | ✓ | ✓ |
| Список пользователей | — | — | ✓ (чтение) | ✓ |
| `user` ↔ `admin` | — | — | — | ✓ |
| Менять роль `super_admin` | — | — | — | — (никто) |
| История изменений | — | — | ✓ | ✓ |

Одна таблица прав в коде — `lib/permissions.ts`; по ней интерфейс показывает кнопки, а Server Actions делают первую проверку. Окончательная проверка — в функциях PostgreSQL по роли из базы.

## 7. Технический вариант

**Выбран:** вариант «как в Mini Booking» — Next.js (App Router, Server Actions) + React + TypeScript + Tailwind CSS 4 + Zod + Prisma 6 + PostgreSQL, npm. Критичные правила живут в PostgreSQL: функции `vm_*`, триггеры, CHECK, EXCLUDE и составные FK.

**Почему:** требования «стол не назначается дважды», «нет двух активных бронирований на одно время» и «правила одинаковы в UI, на сервере и в базе» надёжнее всего закрываются ограничениями базы; подход уже проверен в уроке 4.3.3.

**Рассматривались и отклонены:**
- Правила только в TypeScript-сервисе — гонки двух одновременных запросов ловятся слабее, база не защищена от обхода.
- Список окон в таблице Slot — противоречит требованию считать окна по правилам; закрытия как исключения проще и честнее.

**Структура:**

```
app/                  страницы, Server Actions (app/actions), компоненты (app/components)
  book/               выбор даты, гостей и окна
  account/            мои бронирования и уведомления
  admin/              бронирования, окна, пользователи, история
lib/
  booking/rules.ts    правила окон (общие для клиента и сервера)
  booking/            запросы и вызовы функций БД, коды ошибок
  permissions.ts      матрица ролей
  session.ts, auth.ts auth-lite
prisma/               schema.prisma, миграции, seed.ts
scripts/check-rules.ts проверка правил на живой базе
docs/                 чек-лист приёмки и журнал проверок
```

## 8. Интерфейс

Визуальная система — `design.md` (Verde Marea: #1F4D3A, #C7A76C, #F5F1E8, #1B1B1B; Cormorant Garamond + Manrope).

Экраны: главная (легенда и вход в бронирование), регистрация, вход, «Забронировать», «Мои бронирования», `/admin` (бронирования с фильтрами), `/admin/slots` (окна 14 дней с занятостью и закрытием), `/admin/users`, `/admin/audit`.

Права ролей видны в интерфейсе: в административном контуре есть плашка «Ваша роль: admin / super_admin» со списком доступных действий и действий, которые доступны только владельцу; на странице «Пользователи» admin видит пояснение, что роли меняет только super_admin, вместо кнопок.

Требования: у каждого списка есть пустое состояние; ошибки сервера показываются рядом с действием; кнопки во время запроса заблокированы; отмены — в два нажатия без системного диалога; интерфейс на русском; ширина от 375 px без горизонтальной прокрутки.

## 9. Ограничения и вне рамок

Не входит в MVP и не добавляется без обновления спецификации:

- внешние интеграции: почта, SMS, мессенджеры, оплата, карты, календари;
- публичный деплой, Docker, CI, мониторинг и другой продакшен-контур;
- восстановление пароля, подтверждение почты, OAuth;
- управление столами и редактор плана из интерфейса (столы и план задаются seed), меню, отзывы;
- изменение бронирования (только отмена и новое бронирование).

Технические: только стек из раздела 7; пароли только `bcryptjs` с 12 раундами; `passwordHash` не выбирается в запросах для интерфейса; настоящий `.env` не попадает в репозиторий.

## 10. Критерии готовности

- Миграции применяются на чистую базу командой `npm run db:deploy`, `npm run db:seed` создаёт super_admin, admin, двух гостей, восемь столов и бронирования во всех статусах.
- Регистрация создаёт `user` с bcrypt-хешем (`$2b$12$…`); вход проверяет `bcrypt.compare`; в HTML и ответах нет `passwordHash`.
- `/book` показывает только окна по правилам раздела 5; понедельник, прошедшее, закрытое и занятое не показываются; при отсутствии подходящего стола окна нет.
- Новое бронирование — `pending`, со столом наименьшей подходящей вместимости; второе активное бронирование на то же время и второй стол на то же окно отклоняются базой.
- Гость отменяет своё бронирование за ≥ 3 ч; позже — кнопки нет, сервер отвечает ошибкой.
- `/admin` недоступен `user`; фильтры по статусу и дате работают; видны стол и `no_show`; кнопки соответствуют таблице переходов; терминальные статусы не меняются.
- super_admin повышает и понижает admin; admin этого не может; роль super_admin никто не меняет.
- История показывает создание, подтверждение, отмену, завершение, no_show, смену роли, закрытие и открытие окна с автором и временем.
- `npm run check:rules` проходит полностью; `npm run typecheck`, `npm run lint`, `npm run build` без ошибок.
- Всё из раздела 9 соблюдено.

## 10а. Критерии готовности версии 2 (пет-проект)

- `/book`: после выбора даты и гостей видна полоса окон с числом свободных столов; выбор окна показывает план зала (SVG), статусы столов совпадают с базой; клик по свободному столу → карточка стола → «Забронировать этот стол» создаёт `pending` именно на этот стол; «Подобрать автоматически» работает как раньше.
- Стол занят другим гостем между показом и кликом → понятная ошибка, план обновляется.
- `check:rules` покрывает `p_table_id`: чужая вместимость, занятый стол, неактивный стол, закрытое окно, гонка двух гостей за один стол.
- План доступен с клавиатуры (Tab по свободным столам, Enter — выбор) и читается скринридером (у стола `aria-label`: код, зона, места, статус); на 375 px план масштабируется без горизонтальной прокрутки.
- Эффекты из `design.md`, раздел 4б, работают и отключаются при `prefers-reduced-motion`.

## 11. Допущения

- Часовой пояс ресторана — Europe/Moscow (без перехода на летнее время).
- «Диапазон 12:00–21:00 с шагом 90 минут» — начала 12:00…19:30, последнее окно заканчивается в 21:00 (решение Артёма, 2026-10-15).
- admin тоже может бронировать стол на себя как гость.
- Администратор подтверждает `pending` и отменяет `confirmed` только до начала окна; `pending` может отменить в любое время; `completed` и `no_show` — только после начала (раздел 4).
