# AGENTS.md — как работать с ИИ над Verde Marea

Этот файл не шаблон кода, а правила планирования. Перед любой задачей агент читает `spec.md` (что делаем и чего не делаем), `design.md` (как выглядит) и `Plan.md` (где мы сейчас).

## Источник правды

- Роли, статусы, переходы, правила окон — только из `spec.md` (разделы 4–6). Нужен новый статус или правило — сначала правка спецификации, потом код.
- Внешний вид — только из `design.md`. Новый цвет, радиус или компонент — сначала в `design.md`.
- Прогресс и решения — в `Plan.md` (этапы и журнал), проверки — в `docs/check-log.md`.

## Как планировать задачу

1. Назвать слой причины: данные (миграция, функция `vm_*`), сервер (Server Action, запрос), интерфейс (страница, компонент) или документация.
2. Правило бизнес-логики меняется во всех трёх местах сразу: `lib/booking/rules.ts` или `lib/permissions.ts` → функция PostgreSQL в новой миграции → интерфейс. Если меняется только одно место — правила разъедутся.
3. Схема меняется только новой миграцией. Применённые миграции не редактируются. После правки — `npx prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --shadow-database-url …` должен быть пустым.
4. Сначала минимальное изменение, потом проверка, потом запись в журнал.

## Безопасность — не обсуждается

- Пароль: только `bcryptjs.hash(password, 12)` и `bcryptjs.compare`. Никаких MD5/SHA и своей соли.
- `passwordHash` не выбирается в запросах для страниц и не попадает в props, ответы и логи.
- Пользователь и роль берутся только из серверной сессии, никогда из формы или параметров.
- Каждая Server Action проверяет право через `lib/permissions.ts`, но окончательное решение — за функцией PostgreSQL. Скрытая кнопка — не защита.
- Настоящий `.env` не коммитится. Исключение по решению Артёма (2026-10-15): демо-пароли seed — фиксированные учебные значения из `.env.example`, они указаны в README, чтобы проверяющий вошёл под каждой ролью. Других паролей в документации нет.

## Проверка после изменений

- `npm run typecheck`, `npm run lint`, `npm run build`.
- `npm run check:rules` — правила на живой базе.
- Ручной сценарий из `docs/acceptance-checklist.md` для затронутого контура. Исправили доступность — перепроверить создание, подбор стола, дубли и админский список. Исправили роли — перепроверить user, admin, super_admin и историю.
- Запись в `docs/check-log.md`: что проверяли, результат, что исправили.

## Чего не делать

- Не добавлять интеграции, деплой, Docker, оплату, почту — см. `spec.md`, раздел 9.
- Не хранить окна списком в базе: окна считаются по правилам, `SlotClosure` — только исключения.
- Не возвращать терминальные статусы в активные.
- Не переписывать работающий слой ради «красоты» без задачи в `Plan.md`.
